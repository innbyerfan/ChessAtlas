# ADR-0004: EF Core schema, versioned migrations, and how they are generated

**Status:** accepted
**Date:** 2026-10-13

## Context

The schema has to change over years without ever losing a user's data. That means explicit
`DbContext` configuration, versioned migrations, controlled seed data, indexes sized for search, and
tests that a fresh database migrates.

## Decision

1. **EF Core 10.0.12 with SQLite**, one explicit `ChessAtlasDbContext`, configurations in
   `Persistence/Configurations/` as `IEntityTypeConfiguration<T>`.
2. **Migrations are the only way the schema changes.** No `EnsureCreated`, no hand-applied DDL.
3. **The migration and model snapshot are generated by CI**, not by hand, by the
   `generate-migrations` workflow.
4. **No bulk data in migrations or seed.** Optional reference data goes through an importer.

## Reasoning

### Why generated rather than hand-written

A hand-written migration can be made to create the right tables and still drift from what the model
actually describes, and the drift only surfaces later as a `has-pending-model-changes` failure or a
broken upgrade. Generating it in CI means the checked-in migration is always produced by the same
EF Core version the build uses.

`generate-migrations` is gated on `[gen-migrations]` in a commit message, regenerates into
`Persistence/Migrations`, applies the result to a throwaway SQLite file to prove it works, and
commits it back. It also publishes its transcript to `ci-artifacts/migrations-log.txt` even on
failure — a design-time model error is invisible in a normal build, and the transcript is what makes
it diagnosable.

### Why no bulk data in migrations

The opening catalogue is 3,865 rows today and is optional. Putting it in a migration would make
every future schema change drag the data along, couple schema history to data history, and make it
impossible to refresh one without the other. It arrives through `OpeningCatalogImporter` as a
user-initiated action instead.

## Consequences

- `tests/ChessAtlas.Infrastructure.Tests/Openings/OpeningCatalogPersistenceTests.cs` asserts that
  `Database.Migrate()` on a fresh SQLite file produces exactly the expected tables, and exercises
  search, paging, deduplication and provenance against that migrated schema.
- `ci.yml` runs `dotnet ef migrations has-pending-model-changes` to catch a model that has moved
  ahead of the checked-in snapshot.
- **SQLite treats NULLs as distinct in unique indexes.** Every nullable column that participates in
  a unique index is value-converted so "no value" is stored as `""` and read back as `null`. Without
  this, `unique(OpeningId, Alias, Language)` accepts unlimited duplicates whenever language is null.
- Enums are stored as `int` via `HasConversion<int>()`, so renaming an enum member does not corrupt
  stored rows — but reordering them does. Enum members must be append-only.
- Backup and restore, and the transaction boundaries around import batches, are required before the
  import feature is called finished.
